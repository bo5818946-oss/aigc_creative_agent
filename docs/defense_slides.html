01 · 问题与目标

为什么不能只做一个聊天框

问题定义

聊天式生成的三个问题

Gap
  1. 关键信息被模型静默补全，用户不知道哪些是确认过的。
  2. 时长、场景、主体一致性无法验证，只能“看起来不错”。
  3. 失败过程不可追溯，看不到调用了什么、错在哪一步。

项目目标

Goal
  • 结构化需求 + Pydantic 数据契约
  • 真实 Python 工具调用，而不是模型自评
  • 四类确定性校验
  • 最多两次修正，失败就停止
  • SQLite 持久化、执行轨迹、可复盘
模型负责创作判断，Python 负责可规则化的验证。

03 · Agent 工作流

八个节点，两种失败，一条修正环路

LangGraph
analyze_requirements → plan_workflow → generate_storyboard → generate_prompts → validate_output → write_director_prompt
通过 → write_director_prompt → finalize_result（completed）
演示模式 → 跳过导演提示词，保留规则拼装兜底
失败且 revision_count < 2 → revise_output → 重新生成提示词 → 重新校验
达到上限或修正失败 → finalize_result（validation_failed / failed）

路由原则

Routing
  • 需求/分镜失败：直接归档，不调用下游工具
  • 校验失败：正常分支，不是异常
  • 修正后：必须重新生成提示词并重新校验
  • 导演提示词失败：明确 failed，不用兜底伪装成功
失败是工作流的一部分；系统不会因为“已经修正过”就跳过验证。

05 · 四类校验

不询问模型“你觉得好不好”

Deterministic

时长

Time

负时长、重叠、空档、前导空档、总时长容差、非有限数字。

场景覆盖

Scene

缺失必需场景失败；重复场景警告；覆盖率统计。

主体一致性

Continuity

连续性锁、主体原样描述、车头/屏幕方向、文本方向矛盾。

提示词质量

Prompt

必要字段、矛盾约束、单镜头多运镜、模型负向提示词/语言差异。

错误 = 阻止通过；警告 = 需要确认，但不直接判定失败。
文本检查不能证明最终画面一致；语义边界写入报告。
检查典型错误严重性
时长总时长 24 秒，目标 30 秒错误
场景缺少必需场景：雪地错误
一致性screen_direction 出现相反错误
提示词胶片颗粒 + 4K 超清错误 / 警告
可复现 · 可测试 · 可解释 06 / 12
06 · 修正循环

最多两次，然后明确停止

Max 2
1Model

有模型

需求 + 当前分镜 + 方向审计 + 具体错误交给 DeepSeek，只修列出的问题。

2Python

无模型

只有“时长是唯一失败项”时，才允许确定性缩放时间线。

3Recheck

重新校验

修正后重新生成提示词，再跑四类校验；不能只改文本就宣布成功。

达到上限

validation_failed

保留最后一次校验报告，错误信息包含“已达到自动修正上限 2 次”。

修正工具失败

failed

模型返回非法 JSON、网络失败或结果无法解析；系统停止，不伪造成功。

不无限循环，不静默重试，不把未通过的结果标记为完成。

07 · 数据与可追溯

每一步都留下真实记录

SQLite

七张表

Schema
表内容
projects需求、任务计划、分镜
executions执行状态、时间、错误
execution_traces节点、工具、参数、摘要
validation_reports四类校验聚合报告
revision_history修正原因、前后摘要、用量
creative_sessions对话、字段来源、方案状态
creative_assets可复用车辆资产

轨迹字段

Trace
  • 节点名、工具名、工具参数
  • 输入摘要、输出摘要
  • 状态、错误、时间
  • 修正编号、原因、前后摘要
  • 模型调用次数、token 用量

轨迹来自真实函数调用和 LangGraph 流式状态。

数据库调整只做增量建表，不删除已有项目数据。
项目历史只读；导出使用唯一文件名，不覆盖已有文件。
