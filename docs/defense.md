**讲稿**

各位老师好，我的项目是 AIGC 智能创作工作流 Agent。它不是把需求直接丢给聊天模型，而是把创作过程拆成需求解析、任务规划、分镜生成、提示词生成、四类校验和有限修正，并把每一步写入数据库。

### 第 2 页 · 问题与目标

**页面内容**

- 单纯聊天式生成的问题：
  - 关键信息被模型静默补全
  - 时长、场景、主体一致性无法验证
  - 失败过程不可追溯
- 项目目标：
  - 结构化需求
  - 真实工具调用
  - 四类确定性校验
  - 最多两次修正
  - 可持久化、可复盘、可测试

**讲稿**

这个项目要解决的不是“能不能生成一段分镜”，而是“生成结果能不能被检查、失败能不能被解释”。所以我把模型放在需求解析、分镜生成和修正这三个需要创作判断的位置，把时长、场景、一致性、字段完整性这些可以规则化的部分交给 Python。

### 第 3 页 · 系统架构

**页面内容**

```text
Streamlit / CLI
      ↓
CreativeProjectService
      ↓
LangGraph 工作流
  ├── DeepSeek / FakeLLM
  ├── 确定性 Python 工具
  └── 四类校验
      ↓
SQLite + Markdown/JSON 导出
```

- 分层：交互层、服务层、Agent 层、工具层、数据层、契约层、评测层
- 技术栈：Python 3.13、LangGraph、DeepSeek、Pydantic、SQLite、Streamlit

**讲稿**

系统分为交互层、应用服务、Agent、工具、数据和契约七层。LangGraph 负责状态和条件路由；Pydantic 负责输入输出契约；SQLite 负责持久化；Streamlit 只负责展示和交互，不把业务逻辑塞在页面文件里。

### 第 4 页 · Agent 工作流

**页面内容**

```text
analyze_requirements
  → plan_workflow
  → generate_storyboard
  → generate_prompts
  → validate_output
      ├── 通过 → write_director_prompt → finalize_result
      ├── 失败且 revision_count < 2 → revise_output → 重新生成提示词 → 重新校验
      └── 达到上限或修正失败 → finalize_result
```

- 需求或分镜失败时直接归档，不调用下游工具
- 校验失败是正常分支，不是异常
- 修正后必须重新生成提示词并重新校验
- 校验通过后由 DeepSeek 写整片导演提示词和逐镜头提示词

**讲稿**

工作流有八个节点。需求解析失败或分镜生成失败时，路由直接进入归档，不会继续调用时长检查器。校验失败会进入修正分支；修正后不是直接宣布成功，而是重新生成提示词、重新跑四类校验。校验通过后，导演提示词节点让 DeepSeek 写整片提示词、连续性圣经和逐镜头提示词；演示模式跳过该节点，保留规则拼装兜底。

### 第 5 页 · 专业分镜与提示词

**页面内容**

- 专业枚举：
  - 景别、机位角度、运镜、灯光、色彩分级、转场、特效、屏幕方向
- 每个镜头包含：
  - 叙事职责、起止动作、主体状态、连续性锁
  - 摄影参数、声音、负向提示词
- 提示词分两层：
  - 真实模式：DeepSeek 写整片导演提示词、连续性圣经和逐镜头提示词；
  - 演示模式：Python 从结构字段拼装兜底，并明确标注
- 导演提示词按项目类型分支：汽车项目写车头方向、轮胎接地和道路连续性；校园/人物/产品项目只写主体资产、走位、视线、空间连续性和节奏，不输出车辆专属章节或“不适用”占位
- 导演提示词包含资产锁定、方向与物理规则、逐段分镜、转场、摄影、声音、负面约束和结尾

**讲稿**

分镜不是一段自由文本，而是带专业电影参数的结构化数据。景别、机位、运镜等使用受控枚举，模型不能自创字段。校验通过后，导演提示词节点让 DeepSeek 把分镜重写成整片导演提示词和逐镜头提示词，而不是由 Python 拼标签。Python 拼装只在演示模式或导演提示词失败时兜底，并在页面上明确标注。

### 第 6 页 · 四类确定性校验

**页面内容**

| 检查 | 主要内容 |
|---|---|
| 时长 | 负时长、重叠、空档、前导空档、总时长容差 |
| 场景覆盖 | 缺失场景、重复场景警告、覆盖率 |
| 主体一致性 | 连续性锁、主体描述、车头/屏幕方向、文本方向矛盾 |
| 提示词质量 | 必要字段、矛盾约束、单镜头多运镜、模型差异 |

- 不询问模型“你觉得好不好”
- 结果分为错误和警告
- 明确记录语义边界

**讲稿**

四类检查都是确定性 Python 工具。比如时长不是让模型判断，而是直接算区间；场景覆盖直接比对必需场景；一致性检查会看连续性锁、主体描述和屏幕方向是否矛盾；提示词检查会抓“胶片颗粒 + 4K 超清”这类冲突。检查结果分错误和警告，避免把提醒误判成失败。

### 第 7 页 · 修正循环

**页面内容**

- 有模型：把需求、当前分镜、方向审计、具体错误交给 DeepSeek
- 无模型：只在“时长是唯一失败项”时确定性缩放时间线
- 最多 2 次
- 达到上限：
  - `validation_failed`
  - 保留最后一次校验报告
  - 错误信息包含“已达到自动修正上限 2 次”
- 修正工具失败：
  - `failed`
  - 不伪造成功

**讲稿**

修正不是无限重试。系统最多修正两次；每次修正都要重新校验。达到上限后状态是 `validation_failed`，不是 `completed`。如果修正工具本身失败，比如模型返回非法 JSON，状态是 `failed`。这两种失败都会保留在数据库和执行轨迹里。

### 第 8 页 · 数据与可追溯

**页面内容**

- SQLite 七张表：
  - `projects`、`executions`、`execution_traces`
  - `validation_reports`、`revision_history`
  - `creative_sessions`、`creative_assets`
- 轨迹记录：
  - 节点、工具、参数、输入/输出摘要、状态、错误、时间
- 创作会话记录：
  - 消息、字段来源、待回答问题、方案、项目 ID
- 修正记录：
  - 编号、状态、原因、前后摘要、工具、token 用量
- 只做增量建表，不删除已有项目数据

**讲稿**

项目、执行、轨迹、校验报告、修正历史、创作会话和车辆资产都进 SQLite。执行轨迹记录的是真实工具调用，不是前端动画。创作会话会记录每个决策来自用户、选择、Agent 推断还是系统默认，并支持刷新后恢复。修正历史会保存修改前后的镜头数和时间线终点，便于复盘。数据库调整只做增量建表，不删除已有数据。

### 第 9 页 · Streamlit 工作台

**页面内容**

- 七个页面，以主动引导对话为入口、提示词包为主结果页：
  1. 创作工作台（一句话 + 主动追问 + 方案确认）
  2. 提示词包
  3. 分镜详情
  4. 校验报告
  5. 执行过程
  6. 项目历史
  7. 导出
- 后台线程 + 队列 + 真实流式状态
- 配置了 DeepSeek 就自动使用真实模型；未配置时明确显示演示模式
- 统一设计系统：深色渐变侧边栏、极光渐变画布、玻璃卡片、渐变主按钮与「Agent 思考过程」面板

**讲稿**

界面有七个页面。工作台现在从一句自然语言开始：每一轮由 DeepSeek 判断下一步是继续追问、给方案还是开始生成，问题、选项和推荐理由都是现场生成的，模型的推理依据会直接显示在对话里，可以逐条核对。用户可以让 Agent 自主决定，也可以逐项修改。确认方案后才进入原有工作流。执行过程读取后台线程里的真实 LangGraph 状态，不是假进度条。工作台不再让用户选择“是否开启 DeepSeek”：配置了密钥就自动使用真实模型，没配置就明确显示演示模式。项目历史从 SQLite 读取，可恢复创作对话；导出生成 UTF-8 Markdown 和合法 JSON，文件名唯一，不覆盖。

## 常见答辩问题

### Q1：为什么不直接让大模型生成完整分镜和提示词？

因为模型输出不可直接验证。项目把需要创作判断的部分交给模型，把时长、场景、字段、方向矛盾等可规则化部分交给 Python。这样既能利用模型能力，又能让结果可检查、可复现。

### Q2：为什么用 LangGraph，而不是一个函数顺序调用？

因为工作流有状态和条件分支：需求失败、分镜失败、校验失败、修正次数达到上限、修正工具失败，走的路径不同。LangGraph 把这些状态和路由显式表达出来，也方便流式输出和测试。

### Q3：四类校验是不是模型自评？

不是。四类校验全部是 Python 工具，不调用模型。它们会误报或漏报，但结果可复现。报告里也明确写了语义边界。

### Q4：为什么最多修正两次？

这是项目设定的上限，用来避免无限循环和不可控的 token 消耗。达到上限后明确标记 `validation_failed`，保留错误报告。上限是可配置的，但当前限制在 0 到 2。

### Q5：修正后为什么还要重新校验？

因为修正可能引入新问题。只改分镜文本就宣布成功，等于绕过验证。系统修正后必须重新生成提示词并重新执行四类校验。

### Q6：系统真的调用 DeepSeek 了吗？

是。需求解析、分镜生成、导演提示词和修正都完成过真实 API 调用。工作台在配置 `DEEPSEEK_API_KEY` 时会自动使用真实模型；本阶段通过真实 API 集成运行跑通了一次从对话构建需求到执行的生成：4 次模型调用（需求解析、分镜、1 次修正、导演提示词）、6 个镜头、1 次修正、completed，最终累计 29390 tokens，导演提示词 2998 字符。默认测试和 20 条评测使用 FakeLLM，不消耗额度；真实 API 测试需要显式开启。

### Q7：20/20 是不是说明所有结果都通过了？

不是。20/20 表示实际行为符合用例预期。13 条 completed，1 条 validation_failed，3 条 failed，3 条工具级。4 条失败是预期内的，用来验证系统不会伪造成功。

### Q8：怎么保证 API Key 不泄露？

密钥只从 `.env` 或环境变量读取；`.env` 和 `.history/` 被 Git 忽略；错误信息脱敏；日志、轨迹和评测报告不包含密钥；评测报告还会扫描密钥样式字符串。

### Q9：为什么没有生成图片或视频？

项目范围是创作工作流和分镜/提示词，不是视频生成平台。没有接入图片/视频 API，因此不能声称已经生成视频。下一步可以在保留“生成前校验、生成后验收”的前提下接入实际生成 API。

### Q10：这个项目和普通聊天机器人最大的区别是什么？

普通聊天机器人只有输入和输出；这个项目有状态图、真实工具、四类校验、最多两次修正、SQLite 持久化、执行轨迹、项目历史、导出和 20 条评测。失败会明确记录，不会被包装成成功。

## 答辩时的诚实边界

以下说法必须避免：

- “系统已经生成视频。”——没有，只生成分镜和提示词。
- “20 条评测全部通过校验。”——不是，20 条是行为符合预期，其中 4 条预期失败。
- “四类校验能保证画面一致。”——不能，只能检查文本和结构。
- “真实模型质量已经全面评测。”——没有，默认评测用 FakeLLM。
- “系统已经部署上线。”——没有，当前是本地 Streamlit 应用。
- “修正一定会成功。”——不保证，最多两次，失败会停止。
